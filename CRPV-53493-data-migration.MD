# CPRV-53493 Утилита миграции данных.

## Задача

Утилита переносящая данные из кластера источника в приемник (кластер приемник).

## Условия и ограничения

* Права на запись во все кеши на кластере приемнике.
* Права на чтение всех кешей на кластере источнике.
* Сетевой доступ до кластера источника и кластера приемника с хоста на котором запускается утилита.
* При использовании клиентской ноды приемник совместимой версии.
* Транзакционная (бизнес) целостность данных поддерживается внешними средствами.
* Для корректного переноса expire time. Часы и часовой пояс на серверных нодах должны быть синхронизированы внешними средствами.
* При использовании CDC, во избежания доп.цикла пересылки нужно сконфигурировать тот же `dcId` на кластере приемнике.
* При переносе данных в чистый кластер с PDS рекомендуется на время переноса отключать WAL:
  * старт - `./control.sh --wal --disable`.
  * финиш - `./control.sh --wal --enable && ./control.sh --checkpoint`.

### Транзакционная (бизнес) целостность данных поддерживается внешними средствами.

Snapshot Isolation - режим запросов(массового чтения) когда все данные будут прочитаны целостно на момент времени равному началу чтения.
Т.е при чтении не будут видны изменения сделанные конкурентными транзакциями.

DataGrid НЕ предоставляет возможность чтения в режиме Snapshot Isolation. 
Это означает, что при массовых чтениях задача исключения изменения данных лежит на пользователе.
В рамках задачи это означает следующее: Если необходимо что бы данные мигрировали в целостном состоянии, то на время миграции необходимо снять нагрузку на запись.

### Работа утилиты 

Утилита работает аналогично dump-reader, cdc-consumer процессам. 
Процесс запуска и настроек логирования должен быть переиспользован из утилит и кода DataGrid.

1. Открывается соединение с кластером источником.
2. Открывается соединение с кластером приемником.
3. Обработка binary metadata. Данные запрашиваются из источника и загружаются на приемник.
4. Обработка type mapping. Данные запрашиваются из источника и загружаются на приемник.
5. Создание кешей (если указан `--no-cache-create` шаг пропускается):
   1. Если в конфиге используются неподдерживаемые тонким клиентом опции - ошибка.
   2. Для каждого кеша, который попадает под фильтр `--cache-group-names` из кластера источника создается кеш на кластере приемнике.
   3. Конфигурация кеша создается с помощью указанного `CacheConfigTransformer`.
   4. Если кеш уже существует: указан флаг `--no-cache-create` идем дальше, иначе ошибка.
6. Чтение данных выполняется с помощью `ScanQuery`.
   1. Создаем очередь задач на чтение. Каждый `ScanQuery` читает 1 партиции (`ScanQuery#setPartition`).
   2. Очередь задача должна быть сформирована таким образом, что бы равномерно нагружать серверные ноды т.е 
      первой в списке идет партиция которая primary на 1 серверной ноде, второй которая primary на второй и т.д. 
   3. Задачи на чтение разбирают read threads. Количенство read threads задается опцией `--read-threads`.
   4. При чтении очередного батча. По дефолту размер батча 1 он кладется в очередь записи.
   5. Чтение происходит с учетом rate limit'а из конфига. Дефолт - нет лимита.
7. Запись данные выполняется с помощью `put`, `putAll`, `putAllConflict` операций.
   1. Каждый write thread забирает задачу из очереди на запись и выполняет операцию записи. 
   2. Запись происходит с учетом rate limit'а из конфига. Дефолт - нет лимита.
8. Если выполнение завершилось с ошибкой(исключением) - код завершения процесса ошибка. Иначе - код завершения успех.

### Перенос метаданных записей

Есть 2 типа метаданных, которые нужно переносить: expire time, conflict version.
Утилита выполняет чтение запрашивая expire time и conflictVersion. 
Если хотя бы для 1 записи из батча заданы метаданные необходимо использовать API позволяющий добавить эту информацию к записи.

В случае использования `DataStreamer` - ошибка.

### Обработка ошибок

При любой ошибке утилита печатает в лог сообщение и завершает работу.

### Логирование

1. Время запуска и параметры.
2. Название перенесенного типа binary metadata.
3. Название перенесенного type mappings.
4. Факт создания(или пропуска создания) кеша и его конфиг после работы `CacheConfigTransformer`.
5. Старт/Финиш чтения партиции с указанием имени кеша. Указывать затраченное время, количество записей, количество обработанных и всего партиций.
6. Каждую минуту выводить количество прочитанных/записанных записей 

### Оценка трудозатрат

40 ч.д

## Описание реализации. ФАЗА2

Для эффективной утилизации ресурсов и минимизации сетевого трафика возможно выполнять чтение и запись на серверных нодах в compute task'ах.
В рамках фаза2 реализуем возможность выполнения переноса с серверных нод кластеров.
При этом надо уметь запускать compute как на кластере источнике так и на кластере приемнике.

### Условия 

1. Сетевой доступ на кластер приемник с нод кластера источника или наоборот
2. P2P class loading или классы утилиты на сервеных нодах.

## Дополнительные возможности, реализуемые по запросу

1. Создание индексов ПОСЛЕ загрузки данных.
2. Использование `IndexQuery` для чтения.
3. Приемник ДРУГАЯ СУБД - pangolin, cassandra, etc.
4. Snapshot isolation чтения - MVCC.
