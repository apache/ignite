## Задача

DataGrid не умеет уменьшать размер файлов на PDS после удаления.
Из-за этой особенности место потребляемое PDS'ом только растет.
В связи с этим затруднен процесс мониторинга.
Нет ответа на вопрос "Сколько еще данных я могу положить в свой кластер?".

Необходимо разработать процесс высвобождения свободного места.

### Пример

1. cache1 - заполнили данными, которые составляют 80% от обьема диска.
2. cache1 - очистили все данные.
3. cache2 - пытаемся заполнить данными, которые составляют 80% от обьема диска.
4. Загрузка заканчивается ошибкой нехватки свободного места.

## Текущие реализованные решения

### Двухфазный "ребаланс"

1. Вывели половину нод (в случае ячеек).
2. Удалили на них PDS.
3. Ввели обратно.
4. При ребалансе место будет заполнено более оптимально и размер файлов уменьшится.

**Данное решение используется на ПРОМ сейчас.**

Недостатки решения:

* Вывод ноды из топологии для очистки PDS.
* Длительное время восстановления - перейстройка индекса и полный ребаланс.
* Системная нагрузка, которая конкурирует за ресусры с пользовательской выполняется на всем кластере (ребаланс).

### Оффлайн дефрагментация

#### Причны неиспользования офлайн дефрагментации

1. **Слабая автоматизация сопровождения**. Процесс офлайн дефрагментации состоит из нескольких последовательных шагов.
   Шаги хорошо поддаются автоматизации. Отсутствие автоматизированных сценариев сопровождения приводит к провалу внедрения

2. Отсутствие тестирования (вообще не пробовали запускать).

#### Процесс офлайн дефрагментации

1. Запланировали задачу.
2. Перезагрузили ноду в режиме maintenance. В кластера она не входит.
3. Дождались выполнения defragmenation процесса.
4. Ввели обратно.
5. После дефрагментации место будет заполнено более оптимально и размер файлов уменьшится.

## Условия и ограничения

* Не идет процесс RU.
* Топология кластера стабильна.
* (?) Нода находится в maintenance режиме - изменение данных не происходит.

## Направления исследования

1. Модификация алгоритма размещения данных, что бы преимущественно задействовать страницы в начале файла.
2. Создание онлайн in-place процесса дефрагментации.
3. Ускорение процесса оффлайн-дефрагментации: существующий код.

### 4. Все кеши в одном наборе файлов

Файлы партиций относятся к 1 кеш-группе - ключевое решение дизайна из-за которого нельзя переиспользовать место на диске пока не удалишь кеш.
Такой же подход реализован несколькими популярными СУБД - PostgreSQL, InnoDB.

Другие СУБД реализуют друго подход - Все таблицы региона хранятс в 1 наборе файлов.
При этом подходе страницы на диске могут быть переиспользованы разными таблицами.
Такой подход реализован в Oracle, SQLServer, DB2.

Такая глубокая модификация движка хранения выглядит обьемной и для практического решения проблемы дефрагментации не подходит.

### 5. Создание онлайн алгоритма перестроения файла партиции.

Перестроение одного или нескольких файлов при котором:

1. Данные из файла партиции вставляются в новый файл. 
2. По окончании вставки файл партиции заменяется на перестроенны.
3. При этом пустые страницы исчезают - размер нового файла будет меньше.

Процесс создает служебную нагрузку на диск, которая будет конкурировать с пользовательской (read, WAL) и другой служебной (checkpoint).

## ФИЧА 0. Онлайн дефрагментация с полным снятием нагрузки

С помощью флагов запрета новых соединений и `KILL CONNECTION`  команд можно снять пользовательский трафик с клатсера.
В этом случае возможно выполнить логику использующуюся в офлайн дефрагментации без остановки нод кластера.

1. Перевели кластер в режим обслуживания. Дождались отключения или принудительно завершили клиентские соединения.
2. Запустили дефрагментацию - нода не перезагружается и не выходит из кластера.
3. Дождались окончания дефрагментации.
4. Перевели кластер в обычный режим.

**Внимание! Для того, что бы данный сценарий работал необходимо остановить нагрузку на запись**

### Настройки:
1. Количество одновременно перестраиваемых файлов. Изменяется в runtime.

### Метрики

1. `boolean` - Признак запущенного процесса.
2. `String[]` - Набор кеш-групп по которым выполняется дефрагментация.
3. `int[]` - Набор партиций, которые надо дефрагментировать.

### Команды

1. Старт - стартует процесс дефрагментации.
   * Вход - список кешей, список нод. Возможность указать "все кеши" и "все ноды".
   * Выход - статус команды. ОК означает процесс начат.
2. Статус - печать статус процесса.
   * Вход - пусто.
   * Выход - список нод на которых идет процесс.
     Для каждой ноды список кешей по которым идет процесс.
     Для каждого кеша список партиций которые нужно перестроить и партиции по которым процесс идет прямо сейчас.
3. Отмена - принудительно завершение процесса. Новые файлы по которым дефрагментация не завершена удаляются. 
   Индекс по последней перестраиваемой партиции вновь перестраивается. Процесс останавливается на всех нодах.
   * Вход - пусто.
   * Выход - статус команды. ОК означает процесс начат.

### Особенности

1. Нужно дополнительное место для хранения дефрагментированных файлов во время перестроения

## ФИЧА 1. Онлайн дефрагментация с частичным снятием нагрузки

С помощью команд maintenance mode for nodes переводим часть нод в режим обслуживания.
Нагурзка с остальных нод кластера не снимается.
Выполняем процедуру дефрагментации аналогично **ФИЧА 0**.
Переводим ноды в обычный режим.

### Особенности

Для эффективной работы необходим исторический ребаланс. 
Иначе, при переводе ноды в обычный режим будет выполнен полный ребаланс с полным перестроением партиций еще раз.

## ФИЧА 2. Онлайн дефрагментации без полного снятия нагрузки

Возможность онлайн перестроения файлов партиции. 

1. Администратор запускает процесс дефрагментации. Параметры:
   * ноды.
   * кеш-группы.
2. Процесс проходит по всем партициям выбранных кеш-групп на каждой указанной ноды.
3. Выполняет процесс дефрагментации файла партиции:
    1. Создает пустой файл партиции.
    2. Создает слушателя изменений данных партиции.
    3. Изменения данных партиции попадает в обе структуры (существующую и новую).
    4. Проходит по существующей партиции и вставляет данные в новую.
    5. При ошибке вставки в новую стркутуру файл удаляется, работа ноды не прерывается.
    6. По окончании прохода, существующий файл заменяется на новый.
4. Восстановление после сбоев: На старте ноды обнаружили файлы дефрагментации - удаляем.

### Настройки:
1. Количество одновременно перестраиваемых файлов. Изменяется в runtime.
2. rate limit в рамках ноды на io операции перестроения. Изменяется в runtime.

### Метрики

1. `boolean` - Признак запущенного процесса.
2. `String[]` - Набор кеш-групп по которым выполняется дефрагментация.
3. `int[]` - Набор партиций, которые надо дефрагментировать.

### Команды

1. Старт - стартует процесс дефрагментации.
    * Вход - список кешей, список нод.
    * Выход - статус команды. ОК означает процесс начат.
2. Статус - печать статус процесса.
    * Вход - пусто.
    * Выход - список нод на которых идет процесс. 
            Для каждой ноды список кешей по которым идет процесс. 
            Для каждого кеша список партиций которые нужно перестроить и партиции по которым процесс идет прямо сейчас.
3. Отмена - принудительно завершение процесса. Новые файлы по которым дефрагментация не завершена удаляются. 
            Процесс останавливается на всех нодах.
    * Вход - пусто.
    * Выход - статус команды. ОК означает процесс начат.

### Особенности

1. IO нагрузка для записи дефрагментированной партиции на диск.
2. Нужно дополнительное место для хранения дефрагментированных файлов во время перестроения.
3. При перестроение без снятия нагрузки может занимать длительное время (мало IO будет выдано для выполнения дефрагментации).

## Оценка трудозатрат

* ФИЧА 0 - 100чд
* ФИЧА 1 - 80чд (возможна только после реализации maintenance mode for nodes).
* ФИЧА 2 - 150чд
