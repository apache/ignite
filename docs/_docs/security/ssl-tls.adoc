= SSL/TLS

:javaFile: {javaCodeDir}/Security.java
:xmlFile: code-snippets/xml/ssl.xml

This page explains how to configure SSL/TLS encryption between cluster nodes (both server and client nodes) and thin clients that connect to your cluster.

== Considerations

To ensure a sufficient level of security, we recommend that each node (server or client) has its own unique certificate in the node's keystore (including the private key).
This certificate must be trusted by all other server nodes.
//This configuration allows for an easier certificate replacement procedure (for example when they are expired).


== SSL/TLS for Nodes

To enable SSL/TLS for cluster nodes, configure an `SSLContext` factory in the node configuration.
You can use the `org.apache.ignite.ssl.SslContextFactory`, which is the default factory that uses a configurable keystore to initialize the SSL context.

== SSL/TLS for Thin Clients and JDBC/ODBC [[ssl-for-clients]]

Ignite uses the same SSL/TLS properties for all clients, including thin clients and JDBC/ODBC connections. The properties are configured within the client connector configuration.

== Upgrading Certificates
If your SSL certificates are about to expire or have been compromised, you can replace them without restarting the nodes, with the link:tools/control-script#reloading-certificates[`control.sh --ssl reload`] command.
If the new certificates are issued by an authority every trust store already holds, only step 2 below is needed.

Peers authenticate each other, so everything has to trust the new authority before anything presents a certificate from it, and the old authority has to stay trusted until nothing presents its certificates.
If trust stores hold node certificates rather than an authority, steps 1 and 4 add and remove those certificates instead.
The command reaches only the nodes in the topology: a node that is down during a step, or is restarted instead, reads the stores when it starts, so give it the current files before it rejoins.
Applications are never reached, so each step says when they need their files.

Edit a copy of each store and rename it over the one in use, as the examples do.
Keep `-noprompt`: without it, keytool run without a terminal leaves the store unchanged and still exits with zero.

. *Trust the new authority.*
Add its certificate to the trust store of every node and application, including the one `control.sh` connects with (`--truststore`), keeping the old one:
+
[source, shell]
----
cp trust.jks trust.jks.new
keytool -importcert -keystore trust.jks.new -alias newca -file newca.crt -noprompt
mv trust.jks.new trust.jks
----
+
Then run `control.sh --ssl reload`.
Before step 2, check on every node that its trust store holds the new authority, for example with `keytool -list -keystore trust.jks -alias newca`.
A reload checks a node's new certificate against the node's own trust store only, so it does not tell whether the node will trust the new certificates of its peers.
Applications have to trust the new authority before step 2: JDBC and ODBC read the store on the next connection, a running thin client has to be restarted.

. *Present the new certificate.*
Install the new certificate into the key store of every node:
+
[source, shell]
----
cp node.jks node.jks.new
keytool -importcert -keystore node.jks.new -alias node -file node.crt -noprompt
mv node.jks.new node.jks
----
+
Then run `control.sh --ssl reload`.
If `node.crt` holds the node certificate without its chain, import the authority certificate into the store first.
The store and the key in it have to open with the one password the node is configured with, and the store has to hold one key entry: with several, the JSSE key manager picks one of them on its own.
A node whose own trust store does not accept its new certificate keeps the old one and is reported as failed.
Applications that present a certificate of their own replace it after step 1 and before step 3; a running thin client has to be restarted.
`node.crt` has to be issued for the key already in the entry `node`, from a request made with `keytool -certreq -alias node`.
If that key is compromised, put a new key and certificate in the entry instead and restart the nodes: a reload does not close the connections opened with the old key.

. *Check that nothing presents the old certificate.*
`control.sh --ssl status` shows the issuer of the certificate every node serves.
For applications, and for whatever nodes and applications are provisioned from, such as images and configuration management, check the issuer of the certificate they hold:
+
[source, shell]
----
keytool -list -v -keystore node.jks -alias node | grep Issuer
----
+
Do not start step 4 until every answer names the new authority: after it, a node that still presents the old certificate is thrown out of the cluster, and an application cannot connect.

. *Stop trusting the old authority.*
Remove its certificate from the trust store of every node and application:
+
[source, shell]
----
cp trust.jks trust.jks.new
keytool -delete -keystore trust.jks.new -alias oldca
mv trust.jks.new trust.jks
----
+
Then run `control.sh --ssl reload`.
A node that never got its new certificate is reported as failed, since its own trust store no longer accepts it.
Applications may do this in any order with the nodes; a running thin client trusts the old authority until it is restarted.

== Renewing Certificates Automatically [[renewing-certificates]]

A node can renew its certificate by itself before it expires, when the certificate is issued by a certificate authority service rather than read from a file.
Set an SSL context factory that implements `RenewableSslContextFactory` as `IgniteConfiguration.sslContextFactory`, `ClientConnectorConfiguration.sslContextFactory` or `ConnectorConfiguration.sslFactory`.
Transports set with the same factory instance share its certificate and renewals.
HTTP REST takes its certificate from the Jetty configuration and is not renewed.

Each call of the factory's `create()` has to return a context with a newly issued certificate.
The node calls it when the certificate in use enters the renewal window, by default the last 15% of its lifetime: a certificate valid for 30 days is renewed 4.5 days before it expires.
The new certificate goes through the same checks as with link:tools/control-script#reloading-certificates[`control.sh --ssl reload`], and is also rejected if its chain expires no later than the one in use.
Take the trusted authorities of the returned context from a source local to the node, such as a trust store file, not from the response of the issuing service: otherwise the check between nodes accepts a certificate from an authority the other nodes do not trust yet.

If a renewal fails, the node keeps its certificate and retries until it succeeds.
If the node cannot tell which certificate a context presents, it does not renew it: the status shows a failed reload with the reason and no next renewal.
The pause doubles after each failure, from 1 minute to 1 hour by default, and a random delay of up to half of it is added.
The pause is also kept within a quarter of the window, but never below the first pause.
Failures are logged as warnings, and as errors once less than half of the window is left or the next attempt would come after expiry.
A successful renewal or `--ssl reload`, which also asks the factory for a new certificate, plans the next renewal by the new certificate.

Each node renews on its own schedule, starting when a transport starts serving the certificate, before the node joins the cluster.
The node log shows every certificate put in use and the next planned renewal, which `control.sh --ssl status` and the `NextRenewalTime` metric also show.

All renewals of a node run in one thread, so a `create()` that blocks stops them all and holds up `--ssl reload`.
Bound every wait well below the pause after the first failure, and stop waiting when the thread is interrupted: this is how a stopping node ends an attempt.
The node does not release what the factory holds, such as a client of the issuing service: release it when the node stops, for example from a lifecycle bean.

The node reads the following methods of `RenewableSslContextFactory` once, when a transport starts serving the certificate.
A node with settings out of range does not start.

[width="100%", cols="30%, 60%, 10%"]
|=================
| Method | Description | Default

|`getRenewBeforeFraction()`
|Share of the certificate lifetime, from its start to the earliest expiry in its chain, left when the node renews it. Greater than `0` and less than `1`.
|`0.15`

|`getRenewBefore()`
|Maximum renewal window, in milliseconds, not negative. The node takes the smaller of it and the window from the share above; `0` means no maximum.
|`0`

|`getRenewalJitter()`
|Share of the window, from `0` to `1`, by which the renewal is brought forward at random, so that nodes whose certificates expire together do not renew them at the same moment. `renewBeforeFraction * (1 + renewalJitter)` must be less than `1`.
|`0`

|`getRenewalRetryMinInterval()`
|Pause after the first failed renewal, in milliseconds, and the shortest time between two attempts. Positive.
|`60000`

|`getRenewalRetryMaxInterval()`
|Longest pause between failed renewals, in milliseconds. Not less than the pause after the first failure.
|`3600000`
|=================

== SslContextFactory Properties

`SslContextFactory` supports the following properties:

[width="100%", cols="30%, 60%, 10%"]
|=================
| Property | Description | Default

|`keyAlgorithm`
|The key manager algorithm that will be used to create a key manager.
|`SunX509`

|`keyStoreFilePath`
|The path to the key store file. This is a mandatory parameter since the SSL context can not be initialized without a key manager.
|`N/A`

|`keyStorePassword`
|The key store password.
|`N/A`

|`keyStoreType`
|The key store type.
|`JKS`

|`protocol`
|The protocol for secure transport. https://docs.oracle.com/en/java/javase/11/docs/specs/security/standard-names.html#sslcontext-algorithms[Supported algorithms,window=_blank].
|`TLS`

|`trustStoreFilePath`
|The path to the trust store file.
|`N/A`

|`trustStorePassword`
|The trust store password.
|`N/A`

|`trustStoreType`
|The trust store type.
|`JKS`

|`trustManagers`
|A list of pre-configured trust managers.
|`N/A`
|=================
