= SSL/TLS

:javaFile: {javaCodeDir}/Security.java
:xmlFile: code-snippets/xml/ssl.xml

This page explains how to configure SSL/TLS encryption between cluster nodes (both server and client nodes) and thin clients that connect to your cluster.

== Considerations

To ensure a sufficient level of security, we recommend that each node (server or client) has its own unique certificate in the node's keystore (including the private key).
This certificate must be trusted by all other server nodes.
//This configuration allows for an easier certificate replacement procedure (for example when they are expired).


== SSL/TLS for Nodes

To enable SSL/TLS for cluster nodes, configure an `SSLContext` factory in the node configuration.
You can use the `org.apache.ignite.ssl.SslContextFactory`, which is the default factory that uses a configurable keystore to initialize the SSL context.
//You can also implement your own `SSLContext` factory.

====

== SSL/TLS for Thin Clients and JDBC/ODBC [[ssl-for-clients]]

Ignite uses the same SSL/TLS properties for all clients, including thin clients and JDBC/ODBC connections. The properties are configured within the client connector configuration.
The client connector configuration is defined via the `IgniteConfiguration.clientConnectorConfiguration` property.

To enable SSL/TLS for client connections, set the `sslEnabled` property to `true` and provide an `SslContextFactory` in the client connector configuration.
You can re-use the <<SSL/TLS for Nodes,SSLContextFactory configured for nodes>>, or you can configure an SSLContext factory that will be used for client connections only.

Then, configure SSL on the client side in the same way. Refer to the specific client documentation for details.

== Reloading Certificates Without Restarting Nodes

If you configure an `SslContextFactory` that can reload its key and trust material, new TLS connections use the reloaded SSL context without restarting nodes.
This applies to discovery, communication, client connector, binary REST, and Java thin-client connections.
Existing connections continue to use the SSL context that was active when they were established.

== Upgrading Certificates

You can replace certificate files and reload them without restarting nodes that use `SslContextFactory`.
The link:tools/control-script#reloading-tls-certificates[`--ssl reload` command] updates TCP transports on all server and thick-client nodes.
It does not reload TLS for the HTTP REST endpoint (Jetty) or external client applications.

. Back up the key and trust store files before replacing them.
Keep their configured paths, store types, and passwords unchanged; changing node configuration requires a restart.
. Make sure every peer trusts both the current and replacement certificates before changing any key store.
This includes cluster nodes and client applications, including the control script.
If the replacement certificates use an already trusted CA, no trust store change is needed.
Otherwise, add the required certificates to the trust stores, replace the files, and run `control.sh --ssl reload`.
Reload trust in external client applications using their own procedures.
Continue only after every affected peer has loaded the updated trust store.
. Replace each key store with the new certificate and its private key, then run `control.sh --ssl reload` again.
Use the link:tools/control-script#connecting-to-cluster[connection parameters] required by your cluster.
The command asks for confirmation; use `--yes` to skip it.
. Check the command result and the reload logs of any failed nodes, then verify a new connection with the replacement certificates.
Established connections continue using their existing TLS context.

If a factory fails to reload, it keeps its previous context, and that node stops reloading its remaining factories.
Successful reloads remain in effect; other nodes continue independently.
Check the affected node's log for error details.
Correct the failed store and run the command again.
To restore the previous certificates, restore the backed-up files and reload again while peers still trust those certificates.

Custom factories must extend javadoc:org.apache.ignite.ssl.AbstractSslContextFactory[].
They must reread key and trust data from their sources on reload and supply the updated context for new connections.
If any factory on a node has another type, the command reports it as unsupported and reloads nothing on that node.
For these factories, follow the same trust-first sequence and restart affected nodes one at a time instead of running reload.
If you configured `trustManagers` directly, the command reuses them instead of reloading a trust store.

== SslContextFactory Properties

`SslContextFactory` supports the following properties:

[width="100%", cols="30%, 60%, 10%"]
|=================
| Property | Description | Default

|`keyAlgorithm`
|The key manager algorithm that will be used to create a key manager.
|`SunX509`

|`keyStoreFilePath`
|The path to the key store file. This is a mandatory parameter since the SSL context can not be initialized without a key manager.
|`N/A`

|`keyStorePassword`
|The key store password.
|`N/A`

|`keyStoreType`
|The key store type.
|`JKS`

|`protocol`
|The protocol for secure transport. https://docs.oracle.com/en/java/javase/11/docs/specs/security/standard-names.html#sslcontext-algorithms[Supported algorithms,window=_blank].
|`TLS`

|`trustStoreFilePath`
|The path to the trust store file.
|`N/A`

|`trustStorePassword`
|The trust store password.
|`N/A`

|`trustStoreType`
|The trust store type.
|`JKS`

|`trustManagers`
|A list of pre-configured trust managers.
|`N/A`
|=================
