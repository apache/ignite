= SSL/TLS

:javaFile: {javaCodeDir}/Security.java
:xmlFile: code-snippets/xml/ssl.xml

This page explains how to configure SSL/TLS encryption between cluster nodes (both server and client nodes) and thin clients that connect to your cluster.

== Considerations

To ensure a sufficient level of security, we recommend that each node (server or client) has its own unique certificate in the node's keystore (including the private key).
This certificate must be trusted by all other server nodes.
//This configuration allows for an easier certificate replacement procedure (for example when they are expired).


== SSL/TLS for Nodes

To enable SSL/TLS for cluster nodes, configure an `SSLContext` factory in the node configuration.
You can use the `org.apache.ignite.ssl.SslContextFactory`, which is the default factory that uses a configurable keystore to initialize the SSL context.
You can also implement your own `SSLContext` factory, see <<Custom SSL Context Factories>>.

====
Ensure that your version of the JVM addresses
link:https://bugs.openjdk.java.net/browse/JDK-8219658[the following issue, window=_blank] that can cause deadlocks
in SSL connections. If your JVM is affected but can't be updated, then set
the link:clustering/network-configuration[`TcpDiscoverySpi.soLinger`] parameter to a non-negative value.

The keystore must contain the node's certificate and private key. For automatic renewal, keep one private key and its X.509 chain in each store. The built-in factory records that chain when it loads the keystore. With no private key or several private keys, certificate metadata is unavailable and automatic renewal cannot be enabled.

The trust store defines which peer certificates the node accepts. JSSE checks trust when a real TLS connection is established. Configure trust on all nodes and clients before replacing certificates.

Configured protocol and cipher suite names must be supported by the JVM. An unsupported name prevents the node from starting.

You can define other properties, such as key algorithm, key store type, or trust manager. See the description of the properties in the <<SslContextFactory Properties>> section.

After starting the node, you should see the following messages in the logs:


[source, text,subs="verbatim,quotes"]
----
Security status [authentication=off, *tls/ssl=on*]

== SSL/TLS for Thin Clients and JDBC/ODBC [[ssl-for-clients]]

Ignite uses the same SSL/TLS properties for all clients, including thin clients and JDBC/ODBC connections. The properties are configured within the client connector configuration.
The client connector configuration is defined via the `IgniteConfiguration.clientConnectorConfiguration` property.

You can re-use the <<SSL/TLS for Nodes,SSLContextFactory configured for nodes>>, or you can configure an SSLContext factory that will be used for client connections only.

== Upgrading Certificates

You can replace certificates without stopping the whole cluster. Choose the stages that apply to your change:

[cols="2,3",opts="header"]
|===
|Change |Stages
|Same CA, already trusted by every node and application
|Replace certificates (stage 2).
|New CA or new self-signed certificates
|Add trust → replace certificates → remove old trust if required (stages 1–3).
|===

Before starting, check peer trust, protocols, cipher suites and client authentication. `control.sh --ssl reload` does not test TLS connections or roll back a context if new connections fail.

=== 1. Trust the New Certificates

*When:* before installing certificates from a new CA or new self-signed certificates. Keep the old certificates trusted throughout the replacement.

* *On every server and client node:* import the new CA certificate into the trust store. For self-signed certificates, import each peer's new certificate, including application client certificates, instead of a CA certificate. After updating the trust stores on all nodes, run link:tools/control-script#reloading-certificates[`control.sh --ssl reload`] once.
* *In every application that connects over SSL:* update its trust store in the same way. This includes the trust store passed to `control.sh` with `--truststore`.

Make running applications load the updated stores:

[cols="2,3",opts="header"]
|===
|Application |How to load the stores
|Java and C++ thin clients
|Restart the running clients.
|JDBC applications using `javax.net.ssl.*` system properties
|Restart the running applications.
|ODBC applications and JDBC applications using connection properties for their stores
|Open new connections. The drivers read the stores for each new connection.
|===

*Before stage 2:* verify that the trust stores or custom trust managers of every node and application accept the new certificates. Neither `--ssl reload` nor `--ssl status` verifies these trust relationships.

=== 2. Replace the Certificates

*When:* every node and application trusts the new certificates. Start with one node, check it, then repeat on the remaining nodes.

. Back up the node's key store. Replace the old certificate and private key with the new certificate, its chain and private key.
. Run `control.sh --ssl reload`, then use `control.sh --ssl status` to check the certificate loaded on that node. The reload command runs on all nodes, even when you changed the files on only one.
. Test new connections before replacing the next node's certificate. Use `control.sh --diagnostic connectivity` to check communication between nodes. Test the client connector and HTTP REST with new connections from your applications.

Before removing old trust, also replace any application client certificate that would no longer be trusted. This includes `control.sh` started with `--keystore`. Make the applications load their updated stores as described in stage 1.

*If a connection fails:* stop the rollout. Correct peer trust and TLS settings, or restore the old key store and run `control.sh --ssl reload` again. The restored chain must still be valid. If the command cannot reach the node, restore its configuration and restart it.

*HTTP REST configured in Jetty XML:* restart the node to load its new HTTP REST certificate. To use reload for future replacements, move its TLS setup to `ConnectorConfiguration.httpSslFactory`, see link:restapi#configuration[REST API configuration].

=== 3. Remove the Old Trust

*When:* all affected nodes and applications use the new certificates, and the old CA or self-signed certificates must no longer be trusted. Skip this stage if the old CA must remain trusted.

. Use `control.sh --ssl status` to check the new certificates on all updated server and client nodes. Verify new connections and check that every affected application has loaded its replacement client certificate.
. Remove the old CA certificate, or the old self-signed certificates, from node and application trust stores. Run `control.sh --ssl reload` for the nodes. Make applications load the updated stores as described in stage 1.

Reload leaves existing connections open. If you are replacing certificates after a private key compromise, also restart nodes one at a time to close connections established with the old certificates.

== Renewing Certificates Automatically

A node can pick up a new certificate without a command, before the current certificate expires.
Renewal is off by default.
To turn it on, set `renewalEnabled` to `true` in every SSL context factory the node uses, then restart the nodes one at a time.
Besides `IgniteConfiguration.sslContextFactory`, a node may use `ClientConnectorConfiguration.sslContextFactory` with `useIgniteSslContextFactory=false`, `ConnectorConfiguration.sslFactory` and `ConnectorConfiguration.httpSslFactory`.

The node does not renew the certificates of a factory without `renewalEnabled`.
Transports configured with the same factory object get the new certificate together.
The node does not renew HTTP REST certificates that you set in the Jetty configuration file.

With renewal on, `SslContextFactory` reads its key store and trust store files again in the renewal window, the last part of the certificate lifetime.
A factory of your own that extends `AbstractSslContextFactory` takes the new certificate from its own source, see <<Custom SSL Context Factories>>.

The `renewBeforeFraction` property sets the size of the window as a share of the lifetime, 15% by default.
Changes to `renewalEnabled` and `renewBeforeFraction` take effect after restarting the node.
For a certificate valid for 30 days, the window starts 4.5 days before the certificate expires.
If a certificate authority in the chain expires before the certificate, the lifetime ends when the authority expires.

Replace the old files with the new ones before the renewal window starts.
Replace them only with files you are ready to use, because the node starts to use them without a command.

Before installing the new context, the node checks the dates of the chain supplied by the factory. The chain must be valid now, and its earliest expiry must be later than that of the chain in use. If a certificate authority in the chain expires first, renew it too.

Prepare trust stores so that nodes and clients accept both old and new certificates during rollout. Renewal does not test peer trust or TLS compatibility. It puts a changed trust store in use only together with a new certificate. To move to a new certificate authority, follow <<Upgrading Certificates>>.

If the files still hold the certificate in use, the node reads them again after a pause.
Each such attempt, failure to read the files, or rejection of a new certificate increments the node's link:monitoring-metrics/new-metrics#ssl[`ssl.ConsecutiveRenewalFailures`] metric.
The pauses grow from 1 minute to at most 1.5 hours.

While the node waits for a new certificate, it logs a warning once a day.
Once less than half of the renewal window is left, or the certificate expires before the next attempt, the node logs an error instead of the warning.
If the node cannot read the files or rejects the new certificate, it logs every failed attempt and tries again.
`control.sh --ssl status` shows when the next renewal is due.

Automatic renewal requires a factory that supplies the single X.509 chain loaded into each SSL context. If `renewalEnabled` is set but this metadata is unavailable, the node does not start.

== SslContextFactory Properties

`SslContextFactory` supports the following properties:

[width="100%", cols="30%, 60%, 10%"]
|=================
| Property | Description | Default

|`keyAlgorithm`
|The key manager algorithm that will be used to create a key manager.
|`SunX509`

|`keyStoreFilePath`
|The path to the key store file. This is a mandatory parameter since the SSL context can not be initialized without a key manager.
|`N/A`

|`keyStorePassword`
|The key store password.
|`N/A`

|`keyStoreType`
|The key store type.
|`JKS`

|`protocol`
|The protocol for secure transport. https://docs.oracle.com/en/java/javase/11/docs/specs/security/standard-names.html#sslcontext-algorithms[Supported algorithms,window=_blank].
|`TLS`

|`renewalEnabled`
|Whether a node picks up a new certificate from its key store by itself before the current one expires.
|`false`

|`renewBeforeFraction`
|Share of the certificate lifetime left when a node starts to renew the certificate, greater than `0` and less than `1`.
|`0.15`

|`trustStoreFilePath`
|The path to the trust store file.
|`N/A`

|`trustStorePassword`
|The trust store password.
|`N/A`

|`trustStoreType`
|The trust store type.
|`JKS`

|`trustManagers`
|A list of pre-configured trust managers.
|`N/A`
|=================

== Custom SSL Context Factories

To take certificates from a source of your own, such as a PKI service, extend `AbstractSslContextFactory` and implement `checkParameters()`, `createKeyManagers()` and `createTrustManagers()`.

For certificate status and automatic renewal, also override the protected `createKeyMaterial()` method. Return a `KeyMaterial` with the key managers and the X.509 chain from the same load, with the node's certificate first.

For a keystore, use `KeyMaterial.fromKeyStore(keyManagers, keyStore)`. It extracts the chain only when the store contains a single private key entry. The base factory attaches this metadata to the SSL context it builds. Do not reread the store or call PKI again to obtain the chain.

A subclass that builds its context in its own `create()` must also override `createNew()` and build the context there from the same source. Otherwise, a reload or a renewal builds the context without the code in `create()`. When building the context yourself, return `new SSLContextWrapper(delegate, parameters, chain)` with the chain used to initialize it.

If the source has no newer certificate yet, return the certificates in use. Automatic renewal counts this as an unsuccessful attempt and tries again after a pause.
If the factory throws an exception, the node logs it as a failure and keeps the certificates in use.

Transports configured with the same factory object share one context and one renewal schedule on each node. Different factory objects are managed separately, even if their settings are identical.

The node calls the factory only when it starts, on a reload and on a renewal.
On each node, Ignite serializes reload and renewal calls to the same factory object. Calls to different factories can run concurrently.

A call that fetches certificates from a remote service must limit how long it takes and stop when its thread is interrupted.
When the node stops, it interrupts an automatic renewal in progress and waits for it to end.

Use a new factory object for every node start. With the same factory object, a node started again in the same JVM gets the context that `create()` built at the first start.

A `Factory<SSLContext>` that does not extend `AbstractSslContextFactory` works with `control.sh --ssl reload`, but not with automatic renewal. Its `create()` must return a new context on every call. Without chain metadata, status reports `certificate metadata is unavailable` and Ignite cannot check certificate dates. With automatic renewal disabled, a reload can replace a context that has chain metadata with one that does not.
